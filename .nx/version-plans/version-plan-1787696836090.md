`rateLimit` takes a list of limits, and a request is sent only when every one of them admits it — a vendor publishing "20 a second and 50,000 a day" is one client rather than two. The claim is a single backend operation, because claiming budgets in turn would leave the first spent whenever the second declined. A limit is keyed by its `name`, which may be left out once per client, where it is `"default"`.

Templates can offer callers a closed menu of rate limits and let them pick one by key, for vendors whose quota depends on a subscription tier. A plan is a list of limits for the root client, or a whole tree of lists keyed by sub-client path. `registerClientTemplate` takes a third argument, an options object `{ rateLimitOptions, defaultRateLimitOption }` holding the plans and the one applied when a caller names none; a template builder receives a second argument, `context: ClientTemplateContext`, carrying the chosen plan's limits and its key. `addTemplateClient` and `addLocalTemplateClient` take `{ rateLimitOption, rateLimitOverrides }` where they took an overrides record (a bare record is still accepted), and `getRateLimitOptions` lists a template's plans.

BREAKING: `rateLimit` no longer accepts a bare limit object — wrap it in a list. This includes `defaultClientOptions.rateLimit` and what a template builder returns; a bare object is now a `ConfigurationError` when the client is built. Budget keys move to `<client>:rateLimit:<limitName>` and `<client>:concurrency:<limitName>`, and the per-grant keys of an `isolated` OAuth2 client likewise, from `<client>:grant:<grantId>:rateLimit` to `<client>:grant:<grantId>:rateLimit:<limitName>` and the same for `:concurrency`, so a rolling deploy would run two key layouts at once and can double the send rate; and a 1.x replica cannot read the template settings or the rate-limit broadcasts 2.0 writes. Stop the fleet and restart it, and expect one burst of up to `maxTokens` per limit after the restart: the old budget keys are orphaned, and a bucket that does not exist reads as full. Overrides a 1.x fleet stored are read back as one-entry lists, but they do not all behave as they did. 1.x skipped an override whose `type` differed from the template default's; 2.0 applies it, so a stored `noLimit` override over a `requestLimit` default lifts the cap. Only an override swapping a `sharedLimit` for budgets of its own, or the reverse, is still skipped. 1.x logged each override it skipped as `… — skipping override`; before upgrading, find those tenants in your logs and re-add them with the limits you mean. `getClientStats().rateLimit` is now a list, one entry per declared limit, each with its `name`. The same list shape replaces the single object everywhere else a limit appears: `getLoadedClients()[].rateLimit`, the `rateLimitUpdated` event's `rateLimit`, each value of `rateLimitOverrides`, and both the argument and the return value of `rateLimitChange` — the types `RateLimitChange`, `RateLimitOverrides`, `RateLimitUpdatedData`, `ClientStatistics` and `CreateClientData` change with them. A `rateLimitUpdated` message whose `rateLimit` is not a list is logged and ignored. `@dianemo/backend-redis` 2.0 requires `@dianemo/core` 2.0.

A custom `DianemoBackend` keeps working for clients with one limit. A client declaring several needs the new optional `acquireMultiLimit` and `releaseMultiLimit`, and is refused at construction without them; `tryAdmitMultiLimit` gives it the no-queue fast path. Every custom backend must now honour the `emptiesBucket` option of `armFreeze` and `setFreezeState` and the `anyGrant` option of `hasThawRequestInProgress` and `tryStartThawRequest`, must leave a freeze standing when a successful thaw probe lands after the window was re-armed, and must keep what it stores across `close()`. Run the suite in `test/conformance.test.ts` against it.

Other behaviour changes:

- A sub-client that declares its own `authentication` stores its tokens under its own name; in 1.x it used its parent's. Grant tokens 1.x stored for such a sub-client are not found, so set them again.
- `addTemplateClient` builds the clients before it stores anything. A config that cannot be built throws `ConfigurationError` and nothing is stored.
- On the `addTemplateClient` path a builder receives the credentials as JSON reads them back, so a `Date` arrives as a string — on the replica that made the call too. `addLocalTemplateClient` passes the caller's object through.
- What a builder returns is deep-copied before plans and overrides apply to it.
- A 5xx or dropped-connection freeze takes the configured back-off, `retryBackoffBaseTime`, rather than the refill interval. Only a 429 freeze is floored at the shortest refill interval.
- The memory backend keeps its data across `close()`, so `stop()` followed by `start()` in the same process keeps its state, and a restarted handler rebuilds its stored template clients on either backend.
- An abort that lands after a request was admitted refunds what it claimed and rejects with `RequestAbortedError`, not axios's `CanceledError`.
- `setGrantTokens` racing a removal of its client discards the write and throws `client_removed`.
- `removeTemplateClient` can be called from a startup hook.
- `use()` checks every plugin name before registering any, so a refused call registers nothing.
