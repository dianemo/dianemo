`rateLimit` takes a list of limits, and a request is sent only when every one of them admits it — a vendor publishing "20 a second and 50,000 a day" is one client rather than two. The claim is a single backend operation, because claiming budgets in turn would leave the first spent whenever the second declined. A limit is keyed by its `name`, which may be left out once per client, where it is `"default"`.

Templates can offer callers a closed menu of rate limits and let them pick one by key, for vendors whose quota depends on a subscription tier. A plan is a list of limits for the root client, or a whole tree of lists keyed by sub-client path. `registerClientTemplate` takes the plans as a third argument, `addTemplateClient` and `addLocalTemplateClient` take `{ rateLimitOption, rateLimitOverrides }` where they took an overrides record (a bare record is still accepted), and `getRateLimitOptions` lists a template's plans.

BREAKING: `rateLimit` no longer accepts a bare limit object — wrap it in a list. This includes `defaultClientOptions.rateLimit` and what a template builder returns; a bare object is now a `ConfigurationError` when the client is built. Budget keys move to `<client>:rateLimit:<limitName>` and `<client>:concurrency:<limitName>`, so a rolling deploy would run two key layouts at once and can double the send rate; and a 1.x replica cannot read the template settings or the rate-limit broadcasts 2.0 writes. Stop the fleet and restart it. Overrides a 1.x fleet stored are read back as lists, so they need no migration. `getClientStats().rateLimit` is now a list, one entry per declared limit, each with its `name`. The same list shape replaces the single object everywhere else a limit appears: `getLoadedClients()[].rateLimit`, the `rateLimitUpdated` event's `rateLimit`, each value of `rateLimitOverrides`, and both the argument and the return value of `rateLimitChange` — the types `RateLimitChange`, `RateLimitOverrides`, `RateLimitUpdatedData`, `ClientStatistics` and `CreateClientData` change with them. A `rateLimitUpdated` message whose `rateLimit` is not a list is logged and ignored. `@dianemo/backend-redis` 2.0 requires `@dianemo/core` 2.0.

A custom `DianemoBackend` keeps working for clients with one limit. A client declaring several needs the new optional `acquireMultiLimit` and `releaseMultiLimit`, and is refused at construction without them; `tryAdmitMultiLimit` gives it the no-queue fast path.
