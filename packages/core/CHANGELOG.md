# 2.0.0 (2026-10-12)

### ⚠️  Breaking Changes

- `rateLimit` takes a list of limits, and a request is sent only when every one of them admits it — a vendor publishing "20 a second and 50,000 a day" is one client rather than two. The claim is a single backend operation, because claiming budgets in turn would leave the first spent whenever the second declined. A limit is keyed by its `name`, which may be left out once per client, where it is `"default"`. ([#5](https://github.com/vivo-us/dianemo/pull/5))

  Templates can offer callers a closed menu of rate limits and let them pick one by key, for vendors whose quota depends on a subscription tier. A plan is a list of limits for the root client, or a whole tree of lists keyed by sub-client path. `registerClientTemplate` takes a third argument, an options object `{ rateLimitOptions, defaultRateLimitOption }` holding the plans and the one applied when a caller names none; a template builder receives a second argument, `context: ClientTemplateContext`, carrying the chosen plan's limits and its key. `addTemplateClient` and `addLocalTemplateClient` take `{ rateLimitOption, rateLimitOverrides }` where they took an overrides record (a bare record is still accepted), and `getRateLimitOptions` lists a template's plans.

  BREAKING: `rateLimit` no longer accepts a bare limit object — wrap it in a list. This includes `defaultClientOptions.rateLimit` and what a template builder returns; a bare object is now a `ConfigurationError` when the client is built. Budget keys move to `<client>:rateLimit:<limitName>` and `<client>:concurrency:<limitName>`, and the per-grant keys of an `isolated` OAuth2 client likewise, from `<client>:grant:<grantId>:rateLimit` to `<client>:grant:<grantId>:rateLimit:<limitName>` and the same for `:concurrency`, so a rolling deploy would run two key layouts at once and can double the send rate; and a 1.x replica cannot read the template settings or the rate-limit broadcasts 2.0 writes. Stop the fleet and restart it, and expect one burst of up to `maxTokens` per limit after the restart: the old budget keys are orphaned, and a bucket that does not exist reads as full. Overrides a 1.x fleet stored are read back as one-entry lists, but they do not all behave as they did. 1.x skipped an override whose `type` differed from the template default's; 2.0 applies it, so a stored `noLimit` override over a `requestLimit` default lifts the cap. Only an override swapping a `sharedLimit` for budgets of its own, or the reverse, is still skipped. 1.x logged each override it skipped as `… — skipping override`; before upgrading, find those tenants in your logs and re-add them with the limits you mean. `getClientStats().rateLimit` is now a list, one entry per declared limit, each with its `name`. The same list shape replaces the single object everywhere else a limit appears: `getLoadedClients()[].rateLimit`, the `rateLimitUpdated` event's `rateLimit`, each value of `rateLimitOverrides`, and both the argument and the return value of `rateLimitChange` — the types `RateLimitChange`, `RateLimitOverrides`, `RateLimitUpdatedData`, `ClientStatistics` and `CreateClientData` change with them. A `rateLimitUpdated` message whose `rateLimit` is not a list is logged and ignored. `@dianemo/backend-redis` 2.0 requires `@dianemo/core` 2.0. The vendor plugins published from dianemo-plugins so far are all 1.x: each declares a peer of `@dianemo/core ^1.0.0` and returns a bare-object `rateLimit` that 2.0 refuses, so none of them works with core 2.0 until it is re-released, and `@dianemo/plugin-kit` 1.0 will not install beside it either. Until then, register the vendor's template yourself with `registerClientTemplate`, and package it with core's own `definePlugin` if you want a plugin.

  A custom `DianemoBackend` keeps working for clients with one limit. A client declaring several needs the new optional `acquireMultiLimit` and `releaseMultiLimit`, and is refused at construction without them; `tryAdmitMultiLimit` gives it the no-queue fast path. Every custom backend must now honour the `emptiesBucket` option of `armFreeze` and `setFreezeState` and the `anyGrant` option of `hasThawRequestInProgress` and `tryStartThawRequest`, must leave a freeze standing when a successful thaw probe lands after the window was re-armed, and must keep what it stores across `close()`. Run the suite in `test/conformance.test.ts` against it.

  Other behaviour changes:

  - A sub-client that declares its own `authentication` stores its tokens under its own name; in 1.x it used its parent's. Grant tokens 1.x stored for such a sub-client are not found, so set them again.
  - `addTemplateClient` builds the clients before it stores anything. A config that cannot be built throws `ConfigurationError` and nothing is stored.
  - On the `addTemplateClient` path a builder receives the credentials as JSON reads them back, so a `Date` arrives as a string — on the replica that made the call too. `addLocalTemplateClient` passes the caller's object through.
  - What a builder returns is deep-copied before plans and overrides apply to it.
  - A 5xx or dropped-connection freeze takes the configured back-off, `retryBackoffBaseTime`, rather than the refill interval. Only a 429 freeze is floored at the shortest refill interval.
  - The memory backend keeps its data across `close()`, so `stop()` followed by `start()` in the same process keeps its state, and a restarted handler rebuilds its stored template clients on either backend.
  - An abort that lands after a request was admitted refunds what it claimed and rejects with `RequestAbortedError`, not axios's `CanceledError`.
  - `setGrantTokens` racing a removal of its client discards the write and throws `client_removed`.
  - `removeTemplateClient` can be called from a startup hook.
  - `use()` checks every plugin name before registering any, so a refused call registers nothing.

- A request's `cost` may name an amount per limit — `{ rpm: 1, itpm: 1_200, otpm: 4_096 }` — for a client whose limits meter different things, as an AI API's requests and tokens per minute do. The object must name every limit the client meters, or the request fails with the new `RequestCostMismatchError`; a number is still charged to every limit. ([#5](https://github.com/vivo-us/dianemo/pull/5))

  A request may `settle` its cost against its response: it reserves an estimate when admitted, and `settle` reports what the response says was used, which the bucket is corrected to. A settlement never charges or credits the current window for an earlier one. A debit is reduced by the refill the bucket discarded at its ceiling since the claim, and that refill is forgiven once in total however many claims were outstanding while it was discarded, so overlapping settlements are each charged in full; a credit is dropped once the bucket has filled to its ceiling since the claim; and a settlement after a freeze, a reset, or the bucket expiring and being recreated applies nothing. A `requestLimit`'s new `maxDebt` lets a settlement take its balance below zero, and `requestOptions.settleWindow` bounds how late a settlement may arrive. A streamed response settles when its stream ends. A request with `settle` or `settleStream` on a backend that cannot settle is refused with `ConfigurationError` `backend_missing_settlement` before anything is spent.

  A failed response's `retry-after` header is now the minimum for both the retry wait and the freeze. `retryOptions.classifyError` decides, ahead of the built-in rules, whether a failure is retried and whether it freezes the fleet, and may set a minimum freeze — so a spend-cap 429 can fail at once instead of freezing the fleet until the cap resets.

  BREAKING: `getClientStats()` reports each request bucket's `cost` as a record keyed by limit name rather than as one number. A queued request's per-limit cost is stored as JSON, which a 1.x replica reads as a cost of 1 against every limit, under-charging a token limit; stop the fleet and restart it, as for the rest of 2.0. For a custom `DianemoBackend`: `acquireMultiLimit`, `releaseMultiLimit` and `tryAdmitMultiLimit` take the cost on each `MultiLimitSpec` rather than as an argument; `QueuedRequest.cost` is `number | Record<string, number>`; `getQueueStats` returns `costByLimit`; a token-bucket claim may carry a `ClaimMark`, recorded beside the bucket at `claimMarkKey(bucketKey, id)`; a bucket must keep an `epoch` naming its incarnation and a running total `forgiven` of the discarded refill settlements have used, and copy both into each mark it writes; and the new optional `settleTokens` and `emptyTokenBucket` back settlement. `RequestCostExceedsBudgetError` names the limit whose ceiling was exceeded when the client has several.

- A request with `responseType: "stream"` now runs until its stream ends rather than until its headers arrive: its concurrency slot stays held, it counts as in flight for shutdown, and its span stays open. A stream ends when its last chunk has passed through to the caller's stream, not when the upstream connection closes, so a slow reader holds the slot until it has read the body; a body of up to about 128 KiB completes even if the caller never reads it. While the stream is open its slot and claim marks are refreshed every third of the shorter of `concurrencySlotTtl` and the claim marks' lifetime, and never more often than every 250 ms, so a half-hour generation keeps its slot without a half-hour TTL delaying crash recovery. A refresh that finds the slot already gone logs one warning per stream. The new `requestOptions.streamTimeout`, an hour by default, closes a stream left open and releases its slot. ([#5](https://github.com/vivo-us/dianemo/pull/5))

  A stream settles when it ends, at what a `settleStream` observer read from the chunks as they passed, or at what the caller reports through `response.dianemo.settle`; the first wins. An observer that reports an error inside the stream freezes the client as a 5xx would; `streamErrorOf`, on `@dianemo/core/request/types`, reads an observer's result the way the handler does. A thaw probe that streams counts as a success at its headers, so a long generation does not hold the fleet's recovery.

  A streamed request that fails at its headers hands the caller the vendor's error body as an unread stream in `error.response.data`, relayed so that it reaches neither the connection nor the request that carried the credentials; read it or destroy it. A body the caller is not handed, such as a retried attempt's, is destroyed for you.

  BREAKING: a streamed request announces `requestDone` twice — with `phase: "headers"` and then `phase: "end"` — so a host counting completions off that channel should count only `phase !== "headers"`. The caller's `response.data` is a `PassThrough` relaying axios's stream rather than axios's stream itself, and is destroyed with `StreamTimeoutError` or `StreamClosedError` when the timeout or a shutdown closes it. For a custom `DianemoBackend`, the new optional `touchConcurrency` and `touchClaimMark` keep a stream's claims alive; without them a stream outliving `concurrencySlotTtl` loses its slot to the reaper.

- A request waiting out a retry's back-off now answers to its `signal`, ending with `RequestAbortedError`, and to `stop()`, ending with `ClientUnavailableError` `handler_stopped`; either way the queue entry it kept is released, and a retry is never sent upstream after `stop()` has returned. An OAuth2 token refresh times out after the client's axios `timeout` or 30 seconds, whichever is shorter, so a client with no `timeout` or one above 30 seconds gets 30, and a request whose `signal` aborts while it waits on one stops waiting without cancelling the refresh for the requests coalesced onto it. ([#5](https://github.com/vivo-us/dianemo/pull/5))

  A queued request whose cost cannot be spent is failed and stepped over rather than blocking its client's queue. A peer registration that cannot be parsed is skipped by role election rather than failing it. `redactUrl` hides a password containing an unencoded `@`, `#` or `?`, redacting when userinfo cannot be told apart from a port followed by a query, and stored credentials are decrypted only against a full-length authentication tag.

  A thaw probe now succeeds on any response that would not itself freeze the client — a 404 or a 400 included — and fails only on a 429, a 5xx, a dropped connection, or a failure `retryOptions.classifyError` freezes on. A probe used to need a 2xx, though a plain 4xx shows the upstream has stopped limiting just as well.

  `stop()` finishes within its documented budget even when the backend stops answering — about 27 seconds at the defaults, inside Kubernetes' 30-second grace period — and leaves no peer-heartbeat timer holding the process open. A SIGTERM, SIGINT or SIGHUP once again ends the host process after the drain: the signal is re-raised once `stop()` finishes unless the host listens for it itself, and a second signal during `stop()` exits at once.

  A thaw probe counts only when the upstream actually answers: a response that would not freeze the client is a success, one that would is a failure, and a probe that was aborted, abandoned before dispatch, refused at connect or reset makes no progress either way. A request declined by a freeze no longer waits out its admission timeout when a confirmation reply is lost, and a stale admission pass no longer frees the concurrency slot of a stream that is still running.

  BREAKING: once `stop()` has finished, `handleRequest` and the template mutations refuse with `ClientUnavailableError` `handler_stopped` rather than starting the handler again; call `start()` to bring it back. A template name that is empty or contains whitespace is refused with `invalid_template_name`, and a sub-client name that is empty or contains `:` or whitespace with `invalid_client_name_segment` — rename any that collided once backend keys normalized whitespace to `_`. An empty or blank `requestName` is refused with the new `ConfigurationError` code `invalid_request_name`. A handler `key` shorter than 32 characters is refused with the new `ConfigurationError` code `key_too_short`, since it is what every stored credential is encrypted under; a new key cannot read what the old one stored, so after changing it add every template client again.

- A queued request claimed by a controller is now a lease: an entry whose claim is not confirmed within `QUEUE_CLAIM_LEASE_MS`, 10 seconds — the claim's reply was lost, or its controller died before dispatching it — is handed out again rather than sitting `inProgress` until its admission times out, and an entry the backend cannot decode is passed over rather than claimed. A freeze that still owes thaw probes now outlives its window by up to a week, re-armed by every probe that succeeds and by the fresh freeze a failed probe arms, rather than expiring a minute after the window and letting the client back to full rate unprobed. The completion ids that keep a redelivered probe from counting twice are kept as long. ([#5](https://github.com/vivo-us/dianemo/pull/5))

  Fractional costs are admitted within a tolerance of `BALANCE_TOLERANCE` times the smaller of the cost and `maxTokens`, so a bucket of 1 admits a hundred claims of 0.01 while a spent bucket with a large ceiling admits nothing more.

  The Redis backend honours an ioredis `keyPrefix` on its connection everywhere: instance discovery, frozen-grant cleanup and every pub/sub channel, so two fleets that differ only by that prefix no longer read each other's peers or messages, and an operation with no key to touch no longer reads or writes the key the bare prefix names. `subscribe([])` is a no-op on both backends. The memory backend now matches Redis on a stored `"inf"` priority and on the byte order of same-score entries.

  The Redis backend's `close()` falls back to `disconnect()` when its subscriber connection does not quit within half a second, so a Redis that has stopped answering cannot hold a shutdown open.

  BREAKING: a key TTL of zero or below, or a non-finite one, passed to any rate-limit operation — the fast paths, `acquireTokens`, `acquireMultiLimit` and `addRequest`, and 2.0's `touchConcurrency`, `touchClaimMark` and claim marks — throws `RangeError` before anything is written, on both backends; it used to expire the shared key, other holders' slots with it. The plain store keeps reading zero or below as "delete now". With an ioredis `keyPrefix` on the connection, 2.0 publishes and subscribes on prefixed channel names where 1.x used bare ones, so 1.x and 2.0 replicas sharing such a connection do not hear each other's broadcasts — one more reason to stop the fleet rather than roll it, as the rest of 2.0 already requires.

  BREAKING: the helpers for implementing a backend moved off the root entry onto the new `@dianemo/core/backend` subpath, which also re-exports the contract types: the queue-score layout (`calculateQueueScore`, `MAX_QUEUE_PRIORITY`, `MAX_QUEUE_RETRIES`, `QUEUE_PRIORITY_BAND`, `QUEUE_RETRY_BAND`, `QUEUE_SCORE_EPOCH_MS`), `QUEUE_CLAIM_LEASE_MS`, the TTL normalisers and their constants (`normalizeTtlSeconds`, `normalizeStateTtlSeconds`, `normalizeTombstoneTtl`, `REDIS_MAX_TTL_SECONDS`, `REQUEST_TOMBSTONE_TTL_SECONDS`, `FREEZE_PROBE_TTL_SECONDS`), the stored-number parsers (`parseStoredNumber`, `parseFiniteStored`, `parsePriority`, `formatStoredCost`, `parseStoredCost`), `claimMarkKey` and `BALANCE_TOLERANCE`. Of these, 1.x exported the queue-score layout, `parsePriority`, `parseStoredNumber`, `normalizeTtlSeconds` and `REQUEST_TOMBSTONE_TTL_SECONDS` from `@dianemo/core`; import them from `@dianemo/core/backend` instead. The rest only ever reached the root entry in unreleased builds of 2.0, so no published version is affected. The contract types — `DianemoBackend`, `QueuedRequest` and the rest — stay on the root too.

  For a custom `DianemoBackend`: the new required `confirmRequest` ends a claim's lease and must refuse one whose stamp is older than `QUEUE_CLAIM_LEASE_MS` by the backend's clock, even when nobody has claimed the entry since; `getNextRequest` must stamp `QueuedRequest.claimedAt` and hand out again an entry whose stamp is older than `QUEUE_CLAIM_LEASE_MS`; a status written through `updateRequest` must clear the stamp; `hasThawRequestInProgress` and `tryStartThawRequest` must not count a probe whose queue claim has lapsed; and `updateThawProgress` must leave a freeze untouched, its lifetime included, when the probe failed. Run the suite in `test/conformance.test.ts` against it.
